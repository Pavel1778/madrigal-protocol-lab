# Проверка GUI

Английский оригинал: [GUI_VERIFICATION.md](../GUI_VERIFICATION.md).

Запись прогона окна на эталонной выгрузке, произведённой модулем захвата, того, что
оно показывает, и дефектов, найденных при этом. Окно запускалось в offscreen-режиме
на тех же файлах, что использует демонстрация:

```
QT_QPA_PLATFORM=offscreen python -m src.ui.main_window \
  --capture tests/corpus/reference_export/corpus_capture_01.normalized.json \
  --rule examples/corpus_rule_v1.json
```

Каждое утверждение ниже наблюдалось на этом прогоне; автоматическая форма того же
сценария — `tests/ui/test_e2e.py`.

## Что открывается

- Заголовок: `Madrigal protocol laboratory - corpus_capture_01.normalized.json`.
- Строка меню: File (Open normalized capture, Open rule, Save result, Quit), Rule
  (Apply to current direction, Apply to whole capture, Compare versions), Report
  (Show REPORT.md, Export Markdown, Export HTML), Help (Quick help, About).
  У каждого меню и пункта есть клавиатурный мнемоник; Quick help — F1.
- Центральный разделитель, три колонки:
  - слева: дерево сессий, группа «Sessions»;
  - центр: селектор направления, легенда-аннотация с цветными чипами и
    hex-просмотр, группа «Bytes»;
  - справа: виджет вкладок с Interpretation, Compare, Report и Version diff.
- Строка состояния: метка провенанса байта слева, индикатор выполнения справа
  (скрыт в покое) и область временных сообщений.
- Вкладка Interpretation, три подвкладки: Rule (редактируемый текст, живая обратная
  связь разбора, дополнение типов полей и кнопки Apply to current direction / Apply
  to whole capture / Load example), Messages (таблица смещения, длины, статуса,
  полей) и Counterexamples.

Легенда — не текстовая метка. Каждый вид байта — образец, нарисованный той же
кистью, что использует hex-просмотр, поэтому `gap` и `ambiguity` показывают свою
штриховку, а имена стоят рядом со своим цветом; легенда не может разойтись с
байтами, которые объясняет.

## Дерево сессий (шаг 1–2)

Открытие `corpus_capture_01` перечисляет три сессии, `s1`, `s2`, `s3`, каждую со
своими двумя направлениями и счётчиком байт на направление.
`capture_capture_defects` перечисляет одну сессию, чей родительский узел помечен
`[gap, ambiguity]` и чьи два дочерних направления подкрашены, так что дефектный поток
виден до открытия. Строка состояния читает
`3 sessions  capture_id sha256:1a2f3637124a  diagnostics none` для чистого захвата.

## Клик по байту и его провенанс (шаг 2)

Выбор сессии `s1`, направления `A_to_B` и клик по байту на смещении 4 перемещает
курсор редактирования на этот байт и пишет в строку состояния:

```
s1 A_to_B  offset 4   packet 3  seq 1001  ts 1700000000.004
```

Индекс пакета, номер последовательности и временная метка берутся из записи
провенанса, покрывающей смещение, поэтому читатель может найти байт в pcap. Это
проверка, которую просит чек-лист интеграции, и она проходит.

## Применение правила (шаг 3–4)

С загруженным `corpus_rule_v1.json` применение к `s1 A_to_B` сообщает
`rule v1  matched=60`. Применение к `s2 A_to_B` сообщает `mismatched=60`, и заголовки
вкладки Messages становятся `Messages (60)` и `Counterexamples (60)`. Выбор первого
контрпримера прокручивает hex-просмотр к его смещению, и строка состояния снова
показывает это смещение. Каждый контрпример привязан к реальным байтам, а не к их
описанию. Направление без несовпадений не остаётся пустым: вкладка Counterexamples
читает `no counterexamples in this direction`, поэтому пустой список никогда не
принимается за чистый результат.

Применение ко всему захвату сообщает
`matched=60, mismatched=80, incomplete=0, ambiguous=0, uncovered=0, not_applicable=140, outdated=0, unknown=0`,
что и есть счётчик, который указывает отчёт об исследовании. Тот же прогон
заполняет вкладку Counterexamples из корпусного отчёта, поэтому вкладка и строка
состояния согласуются, и каждый корпусный контрпример несёт свою сессию и
направление; клик по нему переключает на ту сессию и направление и прыгает к его
байтам.

`File - Save result` пишет контрактный результат: файл проходит проверку по
`docs/schemas/result.schema.json` и несёт `contract_version`, `rule_id`,
`rule_version`, `capture_id`, `messages` и `summary`, поэтому сохранённый результат —
той же формы, что производит командная строка.

## Diff версий (шаг 5)

После применения v1 ко всему захвату, загрузки `corpus_rule_v2.json` и применения ко
всему захвату вкладка Version diff показывает:

```
report v1 -> v2
  resolved counterexamples: 80
  introduced counterexamples: 0
  unchanged mismatches: 0
  matched delta: +80
  coverage delta: +0.000
```

Это `src.hypothesis.diff.diff_reports`, отрисованный в окне, поэтому уточнение видно
как разрешённые и внесённые контрпримеры, а не как голое изменение чисел.

## Панель гипотез (шаг 4b)

Вкладка Hypotheses заполняется каждый раз при применении правила и читает правило
против сообщений, к которым оно применимо. Применение к одному направлению оценивает
кандидатов по этому одному потоку; применение ко всему захвату (Rule, Apply to whole
capture) оценивает их по каждому потоку в области, и именно на этом сравнении
принимается уточнение. С `corpus_rule_v1.json`, применённым ко всему захвату, вкладка
перечисляет по одной строке на каждого кандидата-чтения каждого поля `hypothesis`
(`command`, `target`, `value`), с полем, именем кандидата, поддержкой, числом
противоречий и баллом. Балл цветокодирован: зелёный на 0.9 и выше, янтарный между
0.5 и 0.9, серый ниже. Для `command` верхние строки — `entropy_enum` и
`low_cardinality` с 1.00 (140 поддержки, 0 противоречий), а строка для `constant`
(чтение, которое объявляет v1) стоит на 0.43 (60 поддержки, 80 противоречий). Выбор
строки испускает первое смещение доказательства и прыгает hex-просмотром к этому
сообщению, тем же прыжком, что делает клик по контрпримеру. Панель ведётся
`src.hypothesis.alternatives.suggest_alternatives`, поэтому показывает собственный
выход движка, а не второе вычисление. `tests/ui/test_hypotheses_view.py` покрывает
цветовые полосы, раскладку «строка на кандидата» и испускаемое смещение, а
`tests/ui/test_main_window.py::test_hypotheses_tab_fills_on_apply` проверяет, что
вкладка заполнена после применения.

## Дефекты, найденные при проверке

Три дефекта были найдены и исправлены в этой ветке; четвёртый предел записан, но не
изменён.

1. Диагностики сессий никогда не заполнялись. `CaptureModel._read_sessions` строил
   каждый `SessionInfo`, не передавая `diagnostics`, поэтому дерево сессий никогда не
   показывало маркер `[gap, ambiguity]`. Исправлено в `src/ui/model.py`.
2. Панели Version diff не существовало: «Compare versions» лишь отправляло сообщение
   в статус. Добавлена вкладка и подключена к `diff_reports` в
   `src/ui/main_window.py` и `src/ui/model.py`.
3. Повторное применение того же правила помечало собственный предыдущий прогон
   outdated, потому что `RuleModel.reload` поднимал версию на каждом вызове. `reload`
   теперь no-op, когда текст не изменился.
4. Теперь в окне есть меню проекта. Переносной проект (`src.project`) можно
   создать, открыть, дополнить текущим захватом и правилом, сохранить,
   экспортировать, импортировать и проверить из строки меню, поэтому шаг 10
   сценария больше не требует командной строки. `tests/ui/test_project_management.py`
   ведёт меню и формат проекта через настоящее окно; путь из командной строки
   (круговой прогон `Project.export` / `Project.import_` с совпадающими
   контрольными суммами захватов) по-прежнему покрыт `tests/ui/test_e2e.py`.

Более поздний проход взаимодействия по тому же окну поднял дальнейшие пункты;
закрытые в этой ветке: прогон корпуса теперь обновляет вкладки Messages и
Counterexamples (они показывали предыдущий прогон по одному направлению); контрпример
можно просматривать из корпусного отчёта; `Save result` пишет контрактную форму выше;
легенда — нарисованные образцы; индикатор выполнения сбрасывается; пустые панели
объясняют себя; диалоги файлов помнят последний каталог.

## Что работает

- Открывает эталонный захват и перечисляет его сессии и направления.
- Отрисовывает байты потока и подсвечивает диагностики на файле дефектов.
- Клик по байту показывает его индекс пакета, номер последовательности и временную
  метку.
- Применение правила показывает matched и mismatched по направлению и по всему
  захвату, с контрпримерами, привязанными к байтам.
- Выбор контрпримера прыгает hex-просмотром к его байтам.
- Diff версий сообщает разрешённые и внесённые контрпримеры.
- Повторное открытие на том же захвате воспроизводит те же вердикты.
- Пустая панель объясняет, почему она пуста: вкладка Messages читает
  `no messages yet - apply a rule...` до любого прогона, а чистое направление читает
  `no counterexamples in this direction`, а не показывает ничего.
- Диалоги файлов помнят последний использованный каталог, поэтому второе открытие не
  начинается снова с корня репозитория.
- Индикатор выполнения сбрасывается в ноль и скрывается по завершении прогона,
  поэтому никогда не показывает устаревшую долю предыдущего прогона.
- Редактор правил даёт живую обратную связь разбора (красный статус на неверном
  тексте, обычный когда правило разбирается) и дополняет типы полей по мере ввода.
- Меню проекта создаёт, открывает, сохраняет, дополняет, экспортирует, импортирует
  и проверяет переносной проект, а также называет и сохраняет текущую версию
  правила — всё через `src.project`.

## Что требует дальнейшей работы

- Интерпретация ответа (`B_to_A`) по полям в поставляемом демо-правиле; окно
  фреймит поток ответа и движок учитывает область `B_to_A`, но демо-правило
  ограничено только `A_to_B`.

## Исправления колонки трафика и строки состояния

Живой проход выше нашёл два места, где значение можно было прочитать лишь частично.
Оба исправлены.

Колонка `traffic` дерева сессий держала соединённую сводку направлений каждой сессии
(`A_to_B:300 B  B_to_A:420 B`), но была размером под свой короткий заголовок, поэтому
второе направление обрезалось при размере окна по умолчанию. Колонка теперь
подгоняется под самую широкую сводку, которую действительно держит, измеренную в
шрифте, которым нарисована каждая строка; отступ заголовка подрезан, чтобы колонка
всё ещё помещалась в панель по умолчанию без полосы прокрутки. Панель, перетащенная
уже значений, останавливает колонку на ширине содержимого и прокручивает вместо
обрезки, потому что нижняя граница заново применяется на каждом изменении размера.

Строка состояния показывает провенанс выбранного байта. Теперь она резервирует
ширину под свой текст (ограниченную, чтобы одна очень длинная строка не оттеснила
индикатор выполнения), несёт полный текст как подсказку и позволяет выделять текст
мышью. Окно, достаточно узкое, чтобы обрезать текст, всё равно показывает всё
значение при наведении.

Оба упражняются на живом дисплее X
(`docs/screenshots/verify/traffic_and_provenance_fix_live.png`): счётчики байт
читаются полностью, а строка провенанса не обрезана. Три теста покрывают поведение:
колонка помещает каждую сводку, колонка держит свою нижнюю границу на узкой панели,
и строка состояния резервирует место и подсказывает свой текст.

## Второй проход на живом дисплее X

Проход выше запускал `QT_QPA_PLATFORM=offscreen`, что упражняет виджеты, но никогда —
оконный менеджер, док, настоящую растеризацию шрифта или настоящий путь ввода.
Поэтому был проведён второй проход на обычном сервере X: `Xvfb :99` при
1680x1050x24 с `openbox` как оконным менеджером и `QT_QPA_PLATFORM=xcb`. Каждый шаг
`docs/demo.md` был пройден настоящими событиями указателя и клавиш (`xdotool`) по
живым координатам виджетов, и окно захватывалось после каждого шага. Захваты лежат в
`docs/screenshots/verify/`.

Что показал живой дисплей сверх offscreen-прохода:

- Окно открывается и остаётся открытым на весь проход; ни один шаг не падает и не
  оставляет устаревшее окно. Существуют два окна верхнего уровня (окно приложения и
  скрытый помощник 1x1), оба принадлежат одному процессу.
- Дерево сессий перечисляет все три сессии с их двумя направлениями и счётчиком байт
  на направление. Колонки помещают свои заголовки.
- Клик по сессии заполняет hex-просмотр; выбор направления `A_to_B` у `s1`
  отрисовывает его 300 байт (`B_to_A` отрисовывает 420); селектор направления и метка
  длины согласуются.
- Заливки видов байт рисуются правильно на живом виджете: применение v1 к захвату
  рисует байты `matched` сплошным зелёным, а байты `mismatched` — штриховкой, и
  образцы легенды используют те же кисти, что байты, которые они подписывают.
- Четыре заливки статусов, используемые для исходов правил, читаются на экране как
  различные; штрихованные виды (`gap`, `ambiguity`, `incomplete`, `mismatched`,
  `ambiguous`) — диагональная текстура поверх цвета поверхности, поэтому
  диагностический диапазон нельзя принять за простое совпадение на глаз.
- Диагностики gap и ambiguity отрисовываются на выгрузке дефектов: `s1 A_to_B`
  рисует 2 байта как `gap` и 22 как `not_applicable`; `s1 B_to_A` рисует 2 как
  `ambiguity` и 48 как `not_applicable` (`docs/screenshots/verify/clean_dark_gap.png`,
  `clean_dark_ambiguity.png`).
- Контраст текста, измеренный по отрисованным пикселям, высок в обеих темах: строка
  меню — 14.1:1 тёмная и 16.0:1 светлая; hex-просмотр — 14.4:1 тёмный и 17.4:1
  светлый.
- Переключение темы ничего не двигает и не меняет размеров. Размеры разделителя,
  геометрия дерева и hex, панель вкладок, меню и строки состояния и две ширины колонок
  дерева идентичны до, во время и после цикла тёмная → светлая → тёмная.
- Все четыре вкладки настроек (General, Editor, Paths, Advanced) отрисовываются как
  различные страницы; каждая открывалась настоящим кликом и захватывалась отдельно.
- Меню View и Help открываются и заполняются над окном
  (`view_menu_open.png`, `help_menu_open.png`).
- Редактор правил разбирает `corpus_rule_v1.json` и сообщает
  `loaded corpus_rule_v1.json  rule v1` в своей строке статуса.

Находки этого прохода, ни одна из которых не падение:

1. Колонка `traffic` показывала два направления соединёнными, например
   `A_to_B:300 B  B_to_A:420 B`. Строке нужно около 193 px, а колонка была 131 px при
   размере окна по умолчанию, поэтому второе направление обрезалось: колонка сессии
   подгоняется под свой заголовок, а колонка трафика растягивается, и данные строки не
   измерялись, поэтому заголовок, который помещается, всё равно мог скрыть за собой
   значение. Это исправлено после прохода (см. «Исправления колонки трафика и строки
   состояния» выше): колонка теперь подгоняется под самую широкую сводку, которую
   держит, и сохраняет эту нижнюю границу при изменении размера.
2. Offscreen-проход сообщал `3 sessions  capture_id ...` в строке состояния, тогда как
   на живом дисплее та же метка была длиннее — `3 sessions capture_id sha2...` — после
   выбора. Метка — тот же виджет; различается лишь видимый префикс, потому что метка
   усечена до левого края строки состояния. Ничего не теряется, но точная строка
   зависит от ширины, поэтому читателю не следует считать её фиксированным значением.

Ничто на живом дисплее не противоречило offscreen-проходу: счётчики, diff версий,
баллы гипотез, провенанс байт и раздел о `Save result` воспроизводятся.

## Переносной проект в командной строке

Переносной проект также проверяется через `src.project.cli` на эталонном захвате,
что упражняет тот же формат, который теперь ведёт меню проекта в окне:

```
python -m src.project.cli pipeline \
  --pcap tests/corpus/corpus_capture_01.pcapng \
  --project /tmp/verifyproj.madrigal --rule examples/corpus_rule_v2.json
```

Это пишет `manifest.json`, `annotations.sqlite`, `captures/`, `results/` и `reports/`.
Контрольная сумма, записанная в манифесте
(`sha256:1a2f3637124abcd43049bdf9432ae3d18024276cf7de29efd43562e0c61f272c`), равна
свежему `sha256sum` скопированного захвата, каталог самодостаточен с относительными
путями, перемещение его в другой каталог и повторное открытие проходит, а `export` в
архив с последующим `import` в новую цель сообщает об отсутствии сломанных файлов.
Поэтому проект переживает перенос между машинами.
