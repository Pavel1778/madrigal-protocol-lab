# Анализ реального корпуса: набор организатора

Английский оригинал: [REAL_CORPUS_ANALYSIS.md](../REAL_CORPUS_ANALYSIS.md).

Организатор предоставил набор захватов для протокола «термостенд». Он закоммичен в
`tests/corpus/real/` и разобран тем же конвейером, что использует приложение,
поэтому эти числа описывают поставляемые файлы и поставляемый код.
Сгенерированный отчёт — `docs/DATASET_INVESTIGATION.md`; команда воспроизведения —
`python -m scripts.investigate_dataset`.

## 1. Что содержит набор

| Файл | Роль |
| --- | --- |
| `research/01_configuration.pcap` | изменения конфигурации и измерения, две TCP-сессии |
| `research/02_variations.pcapng` | другие настройки, отрицательные температуры, метки нескольких длин, кириллица, отвергнутые запросы |
| `research/03_combined_messages.pcap` | несколько действий в одной отправке клиента, разные разбиения на пакеты |
| `additional/04_new_observations.pcapng` | второй эксперимент с другими значениями и размерами пакетов |
| `diagnostics/01..08` | варианты третьей записи, каждый с одним условием захвата или целостности |
| `action_journal.csv` | 109 действий с параметрами, временем и результатом, который показал клиент |
| `dataset_manifest.json` | состав набора и происхождение данных |

Собственный `README_RU.md` организатора указывает происхождение: байты приложения
приходят из реального TCP-обмена клиента/симулятора через сокет на localhost, тогда
как фрейминг Ethernet/IP/TCP, сегментация и часы сгенерированы. Набор — проверка
функций протокола, а не пассивный захват устройства.

`dataset_manifest.json` записывает ожидаемые счётчики сессий и действий на
исследовательский захват. Конвейер воспроизводит счётчики сессий точно.

## 3. Фрейминг сообщений и правила

Протокол описывают два правила: `examples/thermostand_request_v2.json`
(направление `A_to_B`) и `examples/thermostand_response_v2.json`
(направление `B_to_A`). Оба используют кадр с префиксом длины, чьё двухбайтовое
поле длины считает четырёхбайтовый заголовок, что несётся как `length_bias: 4`.

| Направление | Сообщений | matched | mismatched | incomplete | ambiguous | uncovered |
| --- | --- | --- | --- | --- | --- | --- |
| запросы | 45 | 45 | 0 | 0 | 0 | 0 |
| ответы | 45 | 45 | 0 | 0 | 0 | 0 |

Каждое сообщение в исследовательских захватах сфреймлено и совпадает, покрывая
100 % байт в обоих направлениях. Счётчик `not_applicable` в отчёте правила — трафик
другого направления, что ожидаемо.

## 4. Определённые поля

| Поле | Тип | Смещение (запрос / ответ) | Заметка |
| --- | --- | --- | --- |
| `magic` | uint16 | 0 / 0 | константа `0xa65c` (42588) |
| `body_length` | uint16 | 2 / 2 | считает четырёхбайтовый заголовок |
| `message_counter` | uint16 | 4 / 4 | прирастает на каждый обмен |
| `message_type` | enum | 6 / 6 | запрос 16/32/48/126, ответ 272/288/304/382 |
| `status` | enum | — / 8 | 0 ok, 1..4 коды ошибок |
| `enabled` | uint8 | 8 / 9 | гипотеза, set-config и ответы config |
| `period_ms` | uint16 | 9 / 10 | гипотеза |
| `threshold_raw` | int16 | 11 / 12 | гипотеза |
| `label` | string | 14 / 15 | гипотеза, длина в предшествующем uint8 |
| `requested_count` | uint8 | 8 / — | запрос read-values |
| `measurement_count` | uint8 | — / 9 | число записей измерений |
| `device_time_ms` | array uint32 | — / 10 | гипотеза, шаг 7 |
| `temperature_raw` | array int16 | — / 14 | гипотеза, шаг 7; масштаб 0.01 °C |
| `alarm` | array uint8 | — / 16 | гипотеза, шаг 7 |

Значения enum были сверены с журналом: каждый раскодированный `message_type`
соответствует действию, которое журнал записывает в то же время.

## 5. Контрпримеры и уточнение

Первое чтение, `examples/thermostand_request_v1.json`, предполагает, что поле длины
считает только нагрузку. На захвате конфигурации оно производит шесть контрпримеров:
первое сообщение сфреймлено на четыре байта короче, поэтому `magic` читается по
неверному смещению, а `message_counter` попадает вне сообщения.

| Правило | matched | mismatched | incomplete |
| --- | --- | --- | --- |
| v1 (длина только нагрузки) | 0 | 5 | 10 |
| v2 (длина включает заголовок) | 45 | 0 | 0 |

Исправление — четырёхбайтовое смещение заголовка (`length_bias: 4`), которое несёт
v2. Контрпримеры — это доказательство; они сохраняются в исследовании, а не
отбрасываются.

## 6. Диагностики

Каждый диагностический захват построен, чтобы упражнять одно условие. Таблица — то,
что пересборщик действительно сообщает.

| Захват | Условие | Сообщено |
| --- | --- | --- |
| `01_retransmission` | ретрансмиссия тех же байтов | дедуплицировано (одна ретрансмиссия записана в `B_to_A`, без дублирующих байтов) |
| `02_reordered` | переупорядоченные пакеты | собрано в порядке последовательности, без пропуска |
| `03_missing_segment` | недостающий сегмент | `gap` |
| `04_snaplen_truncated` | обрезанный снимок | `gap` |
| `05_conflicting_overlap` | конфликтующее перекрытие | `ambiguity` |
| `06_missing_beginning` | нет начала соединения | `syn_seen=False`, роли последовательности UNKNOWN, поток всё равно построен |
| `07_checksum_offload` | частичная контрольная сумма псевдозаголовка | `checksum_offload`, когда проверка включена |
| `08_bad_checksum` | неверная контрольная сумма | `checksum_offload`, когда проверка включена |

Проверка контрольных сумм выключена по умолчанию из-за offloading; последние две
строки появляются только с `ignore_checksums=False`.

## 7. Корреляция с журналом

Журнал действий держит 109 записей. Применение правила запроса к захвату
конфигурации и корреляция с журналом даёт:

```
14 of 14 messages correlated, 95 journal entries unmatched
```

Каждое раскодированное сообщение-запрос отображается на выполняемое им действие
оператора, а раскодированные параметры согласуются с записанными значениями.
Несопоставленные записи принадлежат другим захватам, которые не были частью того
прогона корреляции.

## 8. Сравнение с синтетическим корпусом

| Свойство | Синтетический корпус | Набор организатора |
| --- | --- | --- |
| Происхождение | сгенерирован от начала до конца | байты приложения из реального сокета, фрейминг сгенерирован |
| Протокол | кадр с префиксом длины, ведущий `0x01` | магия `0xa65c`, длина, считающая заголовок |
| Исследовательские захваты | 1 основной + 1 отложенный | 3 исследовательских + 1 дополнительный |
| Захваты дефектов | 1 объединённый | 8, по одному условию каждый |
| Сообщений | 280 сфреймленных | 90 (45 + 45) |
| Исход правила | v1 даёт 80 контрпримеров, v2 их убирает | v1 даёт 6 контрпримеров, v2 их убирает |

Оба корпуса упражняют один и тот же цикл уточнения: наивное правило, контрпримеры,
привязанные к байтам, версионированное исправление и чистая проверка после него.
Набор организатора добавляет более тонкое покрытие дефектов (восемь захватов с
одним условием) и второй, независимый протокол с другим соглашением фрейминга.

## 9. Применимость и ограничения

- Правила подтверждены на 90 сообщениях по четырём захватам, а не доказаны.
  Организатор утверждает, что заголовки фрейминга сгенерированы, поэтому
  поведение уровня заголовков, видимое здесь, следует перепроверить на пассивном
  захвате.
- `temperature_raw` — гипотеза с масштабом 0.01 °C; положительность масштаба
  опирается на значения журнала, а не на байтовый инвариант.
- Массивы измерений используют фиксированный шаг в семь байт; запись другой длины
  сообщалась бы как `incomplete`, а не молча прочиталась неверно.
- Ответы об ошибках несут однобайтовое тело, поэтому поля конфигурации после
  `status` корректно вне сообщения.
