# Техническое руководство для защиты

Этот файл — для автора, не для жюри. Он объясняет проект простыми словами,
разбирает демонстрационный пример, даёт словарь терминов и заготовки ответов.
Речь по слайдам — в `presentation/defense_script.md`; полные формулировки
вопросов — в `docs/DEFENSE_FAQ.md` (28 вопросов) и `docs/FAQ_FOR_JUDGES.md`
(15); краткая выжимка — в `presentation/Q_and_A.md`.

Все числа взяты из `docs/METRICS.md`, `docs/REFERENCE_INVESTIGATION.md`,
`docs/REAL_CORPUS_ANALYSIS.md` и `docs/BENCHMARK.md`; ни одно не выдумано.

## А. Проект простыми словами

**Какую проблему решает.** Есть записанный сетевой обмен (файл pcap/pcapng) и
журнал действий устройства. Спецификации протокола нет. Нужно получить
проверяемую интерпретацию структуры сообщений: где чтение подтверждается
данными, а где перестаёт работать.

**Какие данные принимает.** Файл захвата PCAP или PCAPNG, правило разбора в
JSON/YAML и, при наличии, журнал действий. Всё это локальные файлы; сеть не
используется.

**Что делает с данными.**

1. Читает пакеты и выделяет TCP-сессии (`src/capture/`).
2. Восстанавливает направленный поток байтов и хранит происхождение каждого
   диапазона: смещение, пакет, sequence number, время.
3. Нарезает поток на сообщения по правилу фрейминга и читает поля
   (`src/protocol/`).
4. Классифицирует каждое сообщение (`matched`, `mismatched`, `incomplete`,
   `ambiguous`, `uncovered`, `not_applicable`, `outdated`, `unknown`).
5. Проверяет правило на всём корпусе и находит контрпримеры
   (`src/hypothesis/`).
6. Сохраняет переносимый проект и отчёт (`src/project/`, `src/report/`).

**Что получает пользователь.** Окно с сессиями, байтами и результатом
применения правила; отчёт Markdown/HTML; машиночитаемый JSON; возможность
повторно применить правило из CLI.

**Что проект не обещает.** Полную расшифровку семантики протокола. Правило
может совпасть на всём корпусе и при этом оставаться гипотезой о смысле поля.
Границы применимости называются явно (слайд 14), а не скрываются.

## Б. Архитектура

Три слоя связаны форматами, а не вызовами: контракты зафиксированы JSON Schema
в `docs/schemas/`. Модуль можно проверить отдельно, ошибка не размазывается по
остальным.

| Компонент | За что отвечает | Вход | Выход | Где видно |
| --- | --- | --- | --- | --- |
| `src/capture/parser.py` | Чтение pcap/pcapng, разбор IP/TCP, диагностика неподдерживаемых уровней | файл захвата | поток `Packet` | список сессий |
| `src/capture/session.py` | Идентификация TCP-сессий по экземпляру соединения | `Packet` | `Session` | дерево сессий |
| `src/capture/reassembly.py` | Восстановление направленного потока: порядок по seq, дедупликация, out-of-order, gap, ambiguity | `Session` + `Packet` | `DirectionalStream` | hex-просмотр |
| `src/capture/provenance.py` | Происхождение диапазона байтов | смещение/длина | `Range` (пакет, seq, время) | строка провенанса |
| `src/protocol/rule.py` | Модель правила и его версий | JSON/YAML | `Rule` | редактор правила |
| `src/protocol/framing.py` | Нарезка потока на сообщения | байты + стратегия | `Message` | границы сообщений |
| `src/protocol/engine.py` | Применение правила, чтение полей | `DirectionalStream` + `Rule` | `FieldResult` | таблица полей |
| `src/hypothesis/corpus.py` | Проверка на корпусе, контрпримеры | правило + корпус | `VerificationReport` | панель проверки |
| `src/hypothesis/status.py` | Классификация статусов | результат | `Status` | цвет байтов |
| `src/report/markdown.py`, `src/report/html.py` | Отчёт | результаты | Markdown/HTML | вкладка отчёта |

**Точки входа (реальные команды):**

```
python -m src.capture.cli  --pcap <f> --out <json>
python -m src.protocol.cli apply --rule <f> --capture <json> --out <result.json>
python -m src.project.cli  pipeline --pcap <f> --project <dir> --report <f>
python -m src.project.cli  create | open | add-capture | export | import
python -m src.ui.main_window --capture <json> --rule <rule.json>
```

**Ключевые функции.** `read_capture` (`parser.py:370`), `build_sessions`
(`session.py:193`), `reassemble` (`reassembly.py:233`), `frame_stream`
(`framing.py:181`), `apply_rule` (`engine.py:541`), `verify_on_corpus`
(`corpus.py:129`), `correlate` (`journal.py:290`).

**Путь данных.** Захват → `read_capture` → `build_sessions` → `reassemble` →
`DirectionalStream` (байты + провенанс + диагностики) → `frame_stream` →
`apply_rule` → статусы → `verify_on_corpus` → отчёт. Каждый шаг пишет результат
в JSON по контракту, поэтому следующий модуль не знает, как получен предыдущий.

## В. Разбор демонстрационного примера

Полный сценарий — в `docs/demo.md` (через окно) и `docs/demo_cli.md` (через
CLI). Ниже — суть.

**Данные.** `tests/corpus/reference_export/corpus_capture_01.normalized.json`
(280 сообщений, 140 запросов) и `corpus_capture_02.normalized.json` (выдержан
отдельно для проверки применимости). Правила — `examples/corpus_rule_v1.json`
и `examples/corpus_rule_v2.json`.

**Что видно в интерфейсе.** Открываем захват: слева сессии, в центре hex, справа
правило и результат, снизу диагностика. Выбираем сессию и направление A→B.

**Гипотеза.** В первом байте запроса предполагаем «код команды». Правило v1
объявляет поле `command` (offset 0, `uint8`) с ожидаемым набором `[1]`, а
`value` — как `uint16` на offset 5 (байты 5–6), помеченное `hypothesis: true`.

**Как устроено правило.** `offset` — смещение от начала сообщения, нумерация с
нуля. `size` — длина поля в байтах. `uint16` — двухбайтовое беззнаковое число;
порядок байтов задаётся `byte_order` (в примере `big`). `framing` описывает, как
поток режется на сообщения: `length_prefixed`, длина на offset 2, два байта,
big-endian, `length_covers: payload`.

**Что считается совпадением.** `matched` — поле прочиталось и не нарушило
правило. `mismatched` — нарушило (например, значение вне `expected`).
`incomplete` — сообщение обрезано пропуском в захвате. `ambiguous` — байты
попадают в конфликтующее перекрытие.

**Что показывает контрпример.** На правиле v1 движок находит 80 несоответствий:
байт команды со значением `2` на offset 0 в сессиях s2 и s3, а ожидался только
`[1]`. Конкретный пример — `02 00 00 03 13 00 55`, `value 2 not in expected [1]`.
Это данные, противоречащие правилу, со ссылкой на исходные байты.

**Уточнение.** Смотрим журнал: команда `2` соответствует действию «изменить
настройку». Правило уточняется до v2: `expected` команды расширен до `[1, 2, 3]`.
Повторная проверка: matched 140, mismatched 0, контрпримеров 0.

**Что подтверждает результат.** На корпусе уточнения 140 из 140 совпали, ноль
контрпримеров, покрытие 0.5 (правило описывает только запросы A→B). Отдельно
правило применено к реальному набору организаторов: 90 сообщений (45 запросов +
45 ответов), все `matched`, precision 1.00. Это подтверждение в проверенной
области, а не доказательство смысла поля.

## Г. Словарь терминов

- **TCP** — транспортный протокол, который передаёт поток байтов, а не готовые
  сообщения приложения. Он не знает, где кончается одно сообщение и начинается
  следующее.
- **Поток байтов** — непрерывная последовательность байтов одного направления
  одного соединения, собранная из пакетов в правильном порядке.
- **Граница сообщения** — место в потоке, где кончается одно сообщение
  приложения и начинается следующее. Определяется форматом протокола, а не
  границами пакетов.
- **Reassembly (пересборка)** — восстановление потока из пакетов: порядок по
  sequence numbers, отбрасывание одинаковых повторов, обработка перестановок и
  пропусков.
- **Sequence number** — номер байта в TCP-потоке; по нему пакеты выстраиваются
  в правильном порядке.
- **Retransmission (повтор)** — повторная передача тех же байтов; не должна
  дублировать байты в потоке.
- **Gap (пропуск)** — место, где сегмент вообще не был записан; помечается явно,
  а не заполняется нулями.
- **Ambiguity (неоднозначность)** — конфликтующее перекрытие: две версии одних
  и тех же байтов расходятся.
- **Hex-просмотр** — показ байтов в шестнадцатеричном виде вместе с ASCII.
- **ASCII** — печатное представление байтов; непечатаемые показываются точкой.
- **Смещение (offset)** — позиция байта или поля от начала сообщения; нумерация
  с нуля.
- **Правило** — формальное описание фрейминга и полей, применимое к новым данным
  без ручного описания каждого сообщения.
- **Фрейминг** — стратегия нарезки потока на сообщения (length-prefixed,
  fixed-size, marker-based, manual).
- **Совпадение (matched)** — поле прочиталось согласно объявленной раскладке.
- **Контрпример** — данные, на которых правило не выполняется; со ссылкой на
  исходные байты.
- **Точность (precision)** — доля сообщений, признанных совпавшими, из всех
  нарезанных. В примере эталон — сама раскладка, поэтому precision это мера
  согласованности правила с данными, а не с внешней истиной.
- **Покрытие (coverage)** — доля байтов потока, объяснённая полями правила.
- **Происхождение (provenance)** — связь диапазона байтов потока с конкретным
  пакетом: файл, индекс, sequence number, время.

## Д. Вопросы жюри

Ниже — короткие честные ответы. Полные версии и ссылки на код — в
`docs/DEFENSE_FAQ.md` и `docs/FAQ_FOR_JUDGES.md`.

1. **Как устроена обработка TCP?** `dpkt` читает pcap/pcapng, `session.py`
   группирует пакеты в сессии по экземпляру соединения, `reassembly.py`
   выстраивает поток по sequence numbers.
2. **Как определяется граница сообщения?** По правилу фрейминга. TCP границ не
   даёт; их задаёт `length_prefixed` (длина на offset 2, `length_covers:
   payload`) или другая стратегия.
3. **Как работает правило?** `apply_rule` режет поток по фреймингу и читает поля
   по `offset`/`size`/типу из `rule.json`.
4. **Что означает смещение байтов?** Позицию от начала сообщения, с нуля. В
   правиле `target` на offset 4, `value` на offset 5.
5. **Как проверяется правильность правила?** `verify_on_corpus` прогоняет
   правило по корпусу и считает статусы и контрпримеры.
6. **Что происходит, когда правило ошибается?** Появляется `mismatched` с
   контрпримером и ссылкой на байты; правило уточняется, версия растёт.
7. **Как устроены тесты?** `pytest`; функциональные тесты на синтетических
   фикстурах и корпусе, отдельные тесты на реассемблинг, фрейминг, версии,
   интерфейс.
8. **Каковы ограничения?** Смысл байта флагов не установлен; `value` остаётся
   гипотезой; правило верно для проверенных захватов и молчит вне них.
9. **Что было самым сложным?** Реассемблинг: повторы, перестановки, пропуски и
   конфликтующие перекрытия при переходе через границу 32-битного sequence
   number.
10. **Почему выбран `dpkt`, а не PyShark?** `dpkt` читает оба формата на чистом
    Python, без внешнего `tshark`; воспроизводится одним `pip install`.
11. **Почему `B_to_A` — `not_applicable`?** Правило ограничено направлением
    A→B (`scope`), поэтому обратное направление вне его области.
12. **Пропуски заполняются нулями?** Нет. Пропуск — явная диагностика `gap`;
    нули исказили бы данные.
13. **Что при конфликтующем перекрытии?** Диагностика `ambiguity`; обе версии
    байтов сохраняются, сообщение не считается совпавшим.
14. **«Совпало везде» — это доказательство?** Нет. Это подтверждение в
    проверенной области. Смысл поля остаётся гипотезой.
15. **Где взять числа?** `docs/METRICS.md`; каждый источник назван, команда
    воспроизведения указана.

Если ответа нет — честно сказать, что это требует отдельной проверки, и назвать,
где её сделать.
